The problem

Why not just do the work in the API call?

A client asks the API to generate a report. Generating it might take seconds, or minutes. If the API does the work itself, the HTTP connection stays open the whole time, and the API is now tightly coupled to how long report generation takes.

The API returns as soon as the job is queued. Processing happens later, on its own schedule. This improves resilience, scalability, burst handling, and failure isolation.

Request lifecycle

What happens on POST /jobs

  1. Client sends POST /jobs with a report request.
  2. API Gateway invokes the Producer Lambda.
  3. Producer validates the body and generates a jobId.
  4. Producer sends the job to SQS.
  5. API responds 202 Accepted — before any processing happens.
  6. Lambda's managed event source mapping polls SQS (no custom polling code).
  7. Worker receives a batch of up to 5 jobs.
  8. Worker processes each job independently.
  9. Successful jobs are deleted from the queue automatically.
  10. Failed jobs become visible again once the visibility timeout expires.
  11. Jobs that fail 3 times move to the dead-letter queue.

Why SQS exists here

A buffer, not just a pipe

SQS sits between the producer and the worker so that submitting a job and processing a job never have to happen at the same rate. It durably stores messages, tracks how many times each one has been delivered, and enforces the visibility timeout that makes retries possible — all without either Lambda writing any queueing logic itself.

Core concept

Understanding the SQS visibility timeout

When the worker receives a message, SQS doesn't delete it right away — it hides it temporarily.

0s — Message receivedWorker Lambda is invoked with this message in its batch.
Message becomes invisibleOther consumers cannot see it while it's "in flight."
Worker processes the jobprocessJob() runs.
Success → deleted, or Failure → left aloneA failure means the message is simply not deleted.
Visibility timeout expires (90s)Comfortably longer than the 15s worker timeout, on purpose.
Message becomes visible again → retriedApproximateReceiveCount increments.

Lambda timeout ≠ SQS visibility timeout. If the visibility timeout were shorter than the time a job actually needs, SQS could redeliver the message to a second worker while the first is still running — duplicate, overlapping processing. That's why this sample sets 90s of visibility against a 15s function timeout.

This is also why SQS is described as at-least-once delivery: a worker may occasionally see the same message more than once, even when everything is configured correctly.

Batch processing

Fewer invocations for the same number of jobs is more efficient and cheaper — but a bigger batch also means a bug that crashes the whole function affects more messages at once. batchSize: 5 keeps that blast radius small and easy to observe.

Core concept — the most important one here

Partial batch failures

Suppose 5 messages are delivered and only one fails:

✓ Job A
✓ Job B
✕ Job C
✓ Job D
✓ Job E

Without a partial batch response, all five would be retried. With one, the worker tells Lambda exactly which message failed:

{
  "batchItemFailures": [
    { "itemIdentifier": "message-id-for-C" }
  ]
}

Only Job C is retried. A, B, D, and E are never reprocessed.

Dead-Letter Queue

A DLQ isolates messages that exhausted their retries (maxReceiveCount: 3 here) so a human can investigate. It does not fix anything automatically — nothing retries or repairs a DLQ message on its own; someone has to look at it and decide what to do.

Everything beyond that capacity simply waits in the queue instead of overwhelming the worker or whatever it calls downstream. Queue depth and message age become a direct, visible measure of this backpressure.

Core concept

Why idempotency matters

Because SQS is at-least-once, not exactly-once:

Worker finishes job
↓
Interruption before delete is acknowledged
↓
SQS delivers the job again

A production worker should check an idempotency store (jobId → COMPLETED, e.g. in DynamoDB) before repeating any side effect. This sample shows exactly where that check would go in src/worker/handler.ts, without adding a database just to demonstrate the idea.

Try it yourself

Submit a job

After deploying (see the README), submit a normal job:

curl -X POST "$API_URL/jobs" \
  -H "Content-Type: application/json" \
  -d '{
    "reportType": "monthly-sales",
    "requestedBy": "demo@example.com"
  }'

Or trigger the retry → DLQ path on purpose:

curl -X POST "$API_URL/jobs" \
  -H "Content-Type: application/json" \
  -d '{
    "reportType": "monthly-sales",
    "requestedBy": "demo@example.com",
    "simulateFailure": true
  }'

Then watch, in order: the API response (still 202), the producer logs, the queue's ApproximateAgeOfOldestMessage, the worker logs (receive count climbing), and finally the dead-letter queue.

Production considerations

Implemented in this sample
