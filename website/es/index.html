Procesamiento Asíncrono de Trabajos con AWS

API Gateway → Lambda → SQS → Lambda

Aprende a desacoplar las solicitudes HTTP del procesamiento en segundo plano usando AWS Lambda, SQS, colas de mensajes fallidos (DLQ), reintentos, procesamiento por lotes, controles de concurrencia y AWS CDK — a través de un ejemplo pequeño, legible y desplegable.

El problema

¿Por qué no hacer el trabajo directamente en la llamada a la API?

Un cliente le pide a la API que genere un reporte. Generarlo puede tardar segundos, o minutos. Si la API hace el trabajo ella misma, la conexión HTTP permanece abierta todo ese tiempo, y la API queda fuertemente acoplada a cuánto tarde la generación del reporte.

En cambio, este ejemplo separa aceptar el trabajo de hacer el trabajo:

La API responde tan pronto como el trabajo queda encolado. El procesamiento ocurre después, según su propio ritmo. Esto mejora la resiliencia, la escalabilidad, el manejo de ráfagas y el aislamiento de fallos.

Ciclo de vida de la solicitud

Qué ocurre en POST /jobs

  1. El cliente envía POST /jobs con una solicitud de reporte.
  2. API Gateway invoca al Producer Lambda.
  3. El producer valida el cuerpo y genera un jobId.
  4. El producer envía el trabajo a SQS.
  5. La API responde 202 Accepted — antes de que ocurra cualquier procesamiento.
  6. El event source mapping administrado por Lambda sondea SQS (sin código de sondeo personalizado).
  7. El worker recibe un lote de hasta 5 trabajos.
  8. El worker procesa cada trabajo de forma independiente.
  9. Los trabajos exitosos se eliminan automáticamente de la cola.
  10. Los trabajos fallidos vuelven a ser visibles cuando expira el tiempo de visibilidad.
  11. Los trabajos que fallan 3 veces se mueven a la cola de mensajes fallidos.

Por qué existe SQS aquí

Un buffer, no solo una tubería

SQS se sitúa entre el producer y el worker para que enviar un trabajo y procesar un trabajo nunca tengan que ocurrir al mismo ritmo. Almacena mensajes de forma durable, rastrea cuántas veces se ha entregado cada uno, y aplica el tiempo de visibilidad que hace posibles los reintentos — todo sin que ninguna de las dos Lambdas tenga que escribir lógica de colas por sí misma.

Concepto clave

Entendiendo el tiempo de visibilidad de SQS

Cuando el worker recibe un mensaje, SQS no lo elimina de inmediato — lo oculta temporalmente.

0s — Mensaje recibidoEl Worker Lambda se invoca con este mensaje en su lote.
El mensaje se vuelve invisibleOtros consumidores no pueden verlo mientras está "en vuelo".
El worker procesa el trabajoprocessJob() se ejecuta.
Éxito → se elimina, o Fallo → se deja intactoUn fallo simplemente significa que el mensaje no se elimina.
Expira el tiempo de visibilidad (90s)Cómodamente mayor que el timeout de 15s del worker, a propósito.
El mensaje vuelve a ser visible → se reintentaApproximateReceiveCount se incrementa.

El timeout de Lambda no es lo mismo que el tiempo de visibilidad de SQS. Si el tiempo de visibilidad fuera más corto que el tiempo real que necesita un trabajo, SQS podría reentregar el mensaje a un segundo worker mientras el primero aún se está ejecutando — procesamiento duplicado y solapado. Por eso este ejemplo configura 90s de visibilidad contra un timeout de función de 15s.

Esto también explica por qué se describe a SQS como de entrega al menos una vez: un worker puede ocasionalmente ver el mismo mensaje más de una vez, incluso cuando todo está configurado correctamente.

Menos invocaciones para la misma cantidad de trabajos es más eficiente y económico — pero un lote más grande también significa que un error que colapsa toda la función afecta a más mensajes a la vez. batchSize: 5 mantiene ese radio de impacto pequeño y fácil de observar.

Concepto clave — el más importante aquí

Fallos parciales en un lote

Supongamos que se entregan 5 mensajes y solo uno falla:

✓ Job A
✓ Job B
✕ Job C
✓ Job D
✓ Job E

Sin una respuesta de fallo parcial del lote, se reintentarían los cinco. Con una, el worker le indica a Lambda exactamente qué mensaje falló:

{
  "batchItemFailures": [
    { "itemIdentifier": "message-id-for-C" }
  ]
}

Solo se reintenta el Job C. A, B, D y E nunca se vuelven a procesar.

Dead-Letter Queue

Una DLQ aísla los mensajes que agotaron sus reintentos (maxReceiveCount: 3 aquí) para que una persona pueda investigarlos. No repara nada automáticamente — nada reintenta o corrige un mensaje de la DLQ por sí solo; alguien tiene que revisarlo y decidir qué hacer.

Concepto clave

Concurrencia de Lambda y contrapresión

Una ráfaga de trabajos llega a la cola más rápido de lo que pueden procesarse:

Solo 2 ejecuciones del worker corren a la vez (reservedConcurrentExecutions: 2):

Worker #1
Worker #2

Todo lo que exceda esa capacidad simplemente espera en la cola en lugar de desbordar al worker o a lo que este llame downstream. La profundidad y la edad de los mensajes en la cola se convierten en una medida directa y visible de esta contrapresión (backpressure).

Concepto clave

Por qué importa la idempotencia

Porque SQS es de entrega al menos una vez, no exactamente una vez:

El worker termina el trabajo
↓
Interrupción antes de confirmar la eliminación
↓
SQS entrega el trabajo de nuevo

Un worker de producción debería consultar un almacén de idempotencia (jobId → COMPLETED, p. ej. en DynamoDB) antes de repetir cualquier efecto secundario. Este ejemplo muestra exactamente dónde iría esa verificación en src/worker/handler.ts, sin agregar una base de datos solo para demostrar la idea.

Recursos creados por CDK

Profundidad de la DLQ, edad del mensaje más antiguo, errores del worker.

Pruébalo tú mismo

Envía un trabajo

Después de desplegar (ver el README), envía un trabajo normal:

curl -X POST "$API_URL/jobs" \
  -H "Content-Type: application/json" \
  -d '{
    "reportType": "monthly-sales",
    "requestedBy": "demo@example.com"
  }'

O activa la ruta de reintento → DLQ a propósito:

curl -X POST "$API_URL/jobs" \
  -H "Content-Type: application/json" \
  -d '{
    "reportType": "monthly-sales",
    "requestedBy": "demo@example.com",
    "simulateFailure": true
  }'

Luego observa, en orden: la respuesta de la API (sigue siendo 202), los logs del producer, el ApproximateAgeOfOldestMessage de la cola, los logs del worker (el conteo de recepciones subiendo), y finalmente la cola de mensajes fallidos.

Yendo más allá

Consideraciones para producción

Implementado en este ejemplo

Procesamiento asíncrono, fallos parciales del lote, DLQ + política de redrive, concurrencia reservada, alarmas básicas, IAM de mínimo privilegio.

Recomendado para producción

Autenticación de la API, un almacén real de idempotencia, una API de estado de trabajos, trazabilidad, notificaciones de alarmas, estrategia de redrive para la DLQ, CI/CD, y pruebas de carga.
